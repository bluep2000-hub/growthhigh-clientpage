# 위프코리아 기업 배포까지의 개발 계획

기준일: 2026-09-18. 목적은 기업에게 전달할 수 있는 운영 상태다.
사용 전 불편을 가정해 신규 기능을 추가하지 않는다. 운영 가능한 기존 페이지를
완성한 뒤 실제 사용 결과로 다음 문제를 정의한다.

## 범위와 완료 기준

- 위프코리아 하나만 개발·이관·검수한다. 다른 기업과 샘플 페이지는 변경하지 않는다.
- 기존 B안, 필터, 즐겨찾기, 📌, 공지, 주요 소통, 프로젝트·일정 화면을 재사용한다.
- 고객 공개와 중요도는 PM이 판단한다. 반복 수집·검증·반영은 시스템이 처리한다.
- 관리 Hub 화면은 만들지 않는다. 고객페이지 안의 PM 인증·권한은 배포 필수 범위다.
- 기업 데이터는 비공개 저장소에만 두고, 서버 인증 전에는 브라우저로 보내지 않는다.
- GitHub에는 코드·명세·검증 기록만 업데이트한다. 위프코리아 데이터 갱신에는
  GitHub Pages·Actions를 사용하지 않는 구조로 전환한다.
- 작업 묶음마다 검사 후 커밋·push하고 로컬과 원격 커밋 일치를 확인한다.

기업 배포 완료는 고객 로그인, 담당자 작업, 고객 반영, 실패 안내·복구,
모바일 사용, 운영 안내가 새 환경에서 연결되고 기존 주소 전환이 검증된 상태다.
DB 생성이나 서버 배포만으로 완료라고 보고하지 않는다.

다른 기업·샘플·Hub 이관은 이번 범위로 확대하지 않는다.

## 1차 작업: 분리된 고객 정상 결과 저장소

### 구조와 데이터

기존 Cloudflare 계정과 Worker·D1 도구를 재사용한다. 새 제품·라이브러리는 추가하지 않는다.
기존 공지 DB `growthhigh-clientpage-notices`와 고객 DB
`growthhigh-clientpage-private`를 분리한다.

- 별도 설정: `worker/wrangler.private.toml`. 기존 `wrangler.toml`은 변경하지 않는다.
- 별도 바인딩: `PRIVATE_DB`. 없으면 실패하며 기존 공지 `DB`로 대체하지 않는다.
- 저장 단위: 고객 공개용 페이지 전체의 완성된 정상 결과 1개.
- 필드: 기업 slug, 실행 키, 수집 시작 시각, 고객용 JSON, 저장 시각.
- 정상 결과 최근 10개를 보관한다. 수집 시작 시각으로 최신 결과를 선택한다.
- 보관 중인 동일 실행 키는 덮어쓰지 않는다. 영구 중복 실행 장부는 아직 아니다.
- 입력 형식·용량 오류는 저장 전에 거절한다. 저장과 이력 정리는 하나의 batch로 실행한다.
- 고객용 HTTP API는 아직 만들지 않는다. `/whiffkorea/health`는 준비 미완료를 표시하고
  다른 경로는 404다. 공개 Worker·미리보기 주소와 운영 route도 비활성 상태다.

현재 검사는 기존 빌더 출력의 최상위·기업 필드 형식을 확인한다.
이것만으로 임의의 중첩 내용까지 고객 공개 승인이 확인되는 것은 아니다.
실제 데이터 연결 전에 기존 `public_talk`과 고객 공개 필터를 재사용하고,
서버 고객 응답의 허용 필드·내부 자료 제외를 2~3차 작업에서 검증한다.

D1 batch의 전체 롤백 동작은 [Cloudflare 공식 명세](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch)에 따른다.

### 상태와 완료 기준

처음에는 결과 없음 → 인증·수집 연결 준비 후 정상 결과 있음.
수집 실패·입력 오류·저장 실패는 기존 정상 결과를 유지한다.
현재 DB에는 실제 기업 데이터를 이관하지 않는다.

1차 작업은 실제 분리 DB 생성·스키마 적용, 저장소 검사, 원격 빈 상태 확인,
GitHub 업데이트로 완료한다. 기업 배포는 5차 작업까지 완료해야 한다.

## 다음 작업: 인증과 권한

고객은 기존처럼 기업 비밀번호 하나를 입력한다. 서버에 확인용 변환값만 저장하고
고객 정보는 세션 검증 후 전달한다. 서버 세션은 고객 로그아웃·기업 비밀번호 변경 시 종료한다.
로그인 실패 제한과 세션 토큰 보호를 구현한다. 비밀번호 원문을 로그·DB·GitHub에 남기지 않는다.

PM은 고객 로그인과 별도의 내부 Google 인증을 사용한다. 관리 Hub 화면 없이
클라이언트페이지에서 로그인하며 Notion의 역할·담당 기업을 확인한다.
기존 담당자 공용 비밀번호는 새 서버의 최종 내부 권한으로 사용하지 않는다.
Google 인증 설정·도메인 연결의 준비 여부는 착수 시 확인하고, 사람만 가능한
설정이 있으면 필요한 한 가지를 설명한다. 이미 승인한 역할·접속 방식을 다시 묻지 않는다.

이관 로그인과 데이터 대조가 끝나기 전에는 Notion 비밀번호 원문을 제거하거나
기존 위프코리아 파일·주소를 변경하지 않는다. 과거 공개 Git 이력에도 산출물이
남을 수 있으므로 현재 파일 제거와 과거 이력 정리를 구분한다. 이력 재작성은 별도 판단 사항이다.

## 운영 지표와 배포 전 조건

| 지표 | 시작·종료 / 분모 | 현재값 | 초기 목표 / 측정 방법 |
|---|---|---|---|
| 인증 전 기업 데이터 전달 | 미인증 요청 → 응답 / 검사 요청 수 | 새 서버 실제 데이터 연결 전, 운영 미측정 | 0건 / HTTP·브라우저 검사 |
| 고객의 관리 작업 허용 | 고객 인증 후 쓰기 요청 → 응답 / 검사 요청 수 | 새 인증 미구현 | 0건 / 권한 검사 |
| 정상 결과 보존 | 수집·저장 오류 → 다음 조회 / 오류 검사 수 | 저장소 검사로 측정, 수집 운영 미측정 | 100% / 이전 결과 대조 |

| 실제 고객 반영 시간 | PM 반영 요청 → 새 고객 화면 확인 / 유효 변경 수 | 기존 구조 파일럿 변경 99.58초·복구 133.26초. 새 구조 미측정 | 새 환경 첫 파일럿 실측 후 목표 결정. 기존 수치를 새 구조 성과로 쓰지 않음 |

30초는 기존 요청의 통신 제한이며 배포 완료 보장이 아니다.
예약 실행이 필요한 갱신은 09·13·18시 기준을 구현 시 명시하고, 접수부터
30분 이내 처리 목표를 이 주기로 보장한다고 쓰지 않는다.

녹음 현재 PC 예약은 기존 PC 실행 중지·장부 확보 전에는 활성화하지 않는다.
확보가 계속 불가능하면 배포 전 수동 실행 운영 방식과 중복 방지 기준을 정하고
자동 예약 미운영을 안내한다. 이미 검증한 녹음 변환 흐름을 미완료로 돌리지 않는다.

실제 데이터와 로그인을 새 환경에서 검수한 뒤에만 주소를 전환한다.
권한·데이터 격리 검사는 새 연결에 대해 수행한다. 기존 기능 자체의 같은
테스트를 완료 증거 없이 다시 요구하지 않는다.

## 구현 기록

- 2026-09-18: 고객 전용 D1 `growthhigh-clientpage-private` 생성. 기존 공지 DB는 유지.
- 1차 코드: `private-store.js`, `private-index.js`, 별도 설정과 첫 스키마.
- 저장소 신규 검사 7개 통과. 실제 기업 데이터 이관·고객 인증·주소 전환은 아직 미실행.
- 로컬 D1과 원격 신규 D1에 `0001_customer_snapshots.sql` 적용 완료.
- 원격 읽기 전용 확인: `customer_snapshots` 0건. 실제 고객 정보 저장 없음.
- Worker 전체 21개 파일·299개 검사 통과 (기존 292 + 신규 7).
- 별도 설정의 Wrangler 배포 dry-run 통과. 실제 고객 서버 배포·공개 주소 생성 없음.
- 기존 운영 Worker·공지 DB·고객 페이지·샘플 산출물은 변경하지 않았다.
- 이 기록과 코드의 GitHub push·원격 커밋 일치는 최종 작업 보고에서 확인한다.

### 2차 작업 진행

- 새 인증 API와 고객·PM 세션을 분리했다. 고객은 관리 API를 사용할 수 없다.
- 인증 스키마 로컬·원격 적용, 기존 비밀번호 확인값 이관·검증 완료. Notion 원문은 유지했다.
