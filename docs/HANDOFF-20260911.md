- 작성·갱신일: 2026-09-11
- 저장소: `https://github.com/bluep2000-hub/growthhigh-clientpage`
- 운영 브랜치: `main`
- 공지 편집기 구현 기준 커밋: `a5a8a8c`
- 운영 페이지: `https://client.growthhigh.co.kr/whiffkorea/?edit#notice`
- 현재 단계: 공지 편집기 운영 배포 완료, 주요 소통 기능 착수 전

## 1. 새 컴퓨터에서 가장 먼저 할 일

1. GitHub Desktop으로 위 저장소를 clone한다.
2. ChatGPT/Codex 데스크톱 앱에서 clone한 `growthhigh-clientpage` 폴더를 로컬 프로젝트의 기본 폴더로 연다.
3. 아래 「새 작업 시작 문구」를 새 작업에 그대로 붙여 넣는다.
4. 새 작업은 이 문서를 먼저 읽고 `git pull`로 `main` 최신 상태를 확인한 뒤 행동해야 한다.

## 2. 제품 목적과 확정된 사용자

이 페이지는 형태가 보이지 않는 컨설팅 서비스의 과정과 결과를 시각화해 고객이
별도로 묻지 않아도 현재 상태, 성과, 다음 일을 파악하게 하는 B2B 고객 포털이다.
최우선 가치는 **누락 방지**와 **투명성**이다.

- 그로스하이 담당자: 미팅 중·직후 공지를 쓰고, 프로젝트 경과·진행현황·향후 일정을 수시로 추가한다.
- 고객사 대표·실무자: 읽기만 한다.
- 담당자 메모와 소통 상태 표시는 주요 소통 MVP에 넣지 않는다.
- 주요 소통은 담당자가 직접 선택하고 고객 화면 상단에 고정한다.
- 모바일 앱은 웹에서 검증한 뒤 결정한다.
- 통화녹음 자동화는 삼성 기본 전화 앱을 사용하는 개인·업무 혼용 스마트폰이 대상이다.
- 개인 통화는 휴대전화 안에서 먼저 제외하고 고객 연락처 그룹의 통화만 외부로 보낸다.

제품 사실과 전체 MVP 범위는 `PRODUCT.md`와 `docs/mvp-상세설계-20260911.md`를 따른다.

## 3. 현재 운영 구조

- 화면: 루트 `index.html`이 원본 템플릿이다.
- 기업 사본: `whiffkorea/index.html` 등은 원본 템플릿에서 생성하며 직접 갈라서 관리하지 않는다.
- 데이터 빌드: Python이 Notion과 외부 데이터를 읽어 `c/{슬러그}.enc`를 만든다.
- 고객 페이지: GitHub Pages의 정적 페이지이며 비밀번호로 암호화된 봉투를 브라우저에서 푼다.
- 공지 원본: Cloudflare D1이다. 새 공지는 노션에 쓰지 않는다.
- 담당자 편집 API: Cloudflare Worker `growthhigh-clientpage-relay`가 제공한다.
- 공지 초안: D1 `notice_drafts`, 고객 게시본: D1 `notices`, 지난 게시본: D1 `revisions`.
- 게시하면 Worker가 GitHub `repository_dispatch`를 보내 해당 기업의 정적 페이지를 재빌드한다.

구조와 운영 규칙은 `CLAUDE.md`, 용어는 `CONTEXT.md`, 결정 이유는 `docs/adr/`를 우선한다.
이 문서와 다른 문서가 충돌하면 날짜가 더 최신인 이 문서와 실제 코드를 먼저 확인한다.

## 4. 완료된 공지 편집기

2026-09-11 사용자가 직접 로컬 미리보기를 확인하고 승인했으며 운영에 배포했다.

### 작성 경험

- 공지 편집 화면을 카드 모음이 아닌 한 장의 문서형 레이아웃으로 변경했다.
- 제목에서 Enter를 누르면 첫 본문으로 이동하고, 본문은 Enter로 자유롭게 이어 쓴다.
- 빈 공지와 빈 목록 항목도 전체 폭을 클릭해 바로 입력할 수 있다.
- 커서 색과 포커스를 보강해 현재 입력 위치가 보인다.
- 저장 전 줄 앞에 나타나던 색 띠를 제거했다.
- 상시 노출되던 줄 삭제, 위·아래 이동, 들여쓰기 버튼과 드래그 손잡이는 숨겼다.
- 들여쓰기는 `Tab`, 내어쓰기는 `Shift+Tab`으로 동작한다. 여러 항목 선택에도 적용된다.
- 삭제해서 빈 항목이 되어도 편집 칸 자체가 사라지지 않고 포커스를 유지한다.
- 작성 중 텍스트가 사라지던 재렌더링 경로를 정리했다.

### 초안과 게시

- 입력이 멈추면 D1 초안에 자동저장한다.
- 자동저장은 고객 화면이나 GitHub 배포를 바꾸지 않는다.
- `미리보기`로 초안을 고객 화면 형태로 확인한다.
- `게시`를 눌러야 고객 게시본으로 승격되고 재빌드가 시작된다.
- 다른 창에서 초안이 먼저 바뀐 경우 판 번호로 어긋남을 막는다.
- 오프라인 임시보존, 재시도, 이전 게시본을 초안으로 불러오는 경로가 있다.

### 마지막 승인 수정

- Tab으로 만든 중첩 문서가 미리보기에서 빠지던 `items`/`children` 자료 구조 차이를 보완했다.
- 편집 화면·미리보기·고객 화면의 할 일 기호를 네모 체크박스로 통일했다.
- 완료 체크된 할 일의 해당 문장에만 취소선을 표시하고 하위 항목에는 전파하지 않는다.
- 최종 자동 테스트: 16개 파일, 263개 모두 통과.

### 운영 배포 기록

- Git 커밋: `a5a8a8c` (`공지 편집기 초안·게시 흐름과 문서형 UI 개선`)
- D1 마이그레이션: `worker/migrations/0003_notice_drafts.sql` 운영 적용 완료
- Worker 배포 버전 ID: `b2dcc153-cca4-47b0-9a78-e62385b7ef0c`
- Worker 상태 확인: `/health` 200, 새 `/notice/doc/draft` 경로는 미인증 요청에 401로 정상 보호
- 운영 페이지에서 초안 API, 중첩 미리보기, 체크 취소선 코드 반영 확인

`0003_notice_drafts.sql`은 운영에 이미 적용됐다. 새 컴퓨터에서는 먼저
`npx wrangler d1 migrations list growthhigh-clientpage-notices --remote`로 상태를 확인하고,
이미 적용된 마이그레이션을 수동 SQL로 다시 실행하지 않는다.

## 5. 다음 작업: 주요 소통 지정

공지 편집기 다음으로 사용자가 확정한 우선순위다. 상세 설계는
`docs/mvp-상세설계-20260911.md`의 「7. 주요 소통 지정」을 따른다.

### 확정 동작

- 담당자 모드에서만 소통 행에 빈 별 `☆`를 표시한다.
- 한 번 누르면 `★`가 되고 같은 항목이 화면 상단 `주요 소통`에 즉시 나타난다.
- 다시 누르면 해제한다.
- 별도 저장 버튼, 담당자 메모, 업무 상태 선택은 없다.
- 고객은 주요 소통을 읽기만 하며 편집 장치를 볼 수 없다.
- 중요도 판단은 자동화하지 않고 담당자가 직접 한다.
- 원본은 현재 Notion 소통 내역 DB의 `주요` 체크박스를 유지한다.

### 설계된 구현 경계

1. 빌더가 각 소통의 Notion 페이지 ID를 SHA-256으로 해시해 앞 24자리 `talk_key`만 암호화 봉투에 넣는다.
2. Worker에 `PUT /talk/major`를 추가한다.
3. Worker는 담당자 인증 후 `talk_key`로 원본을 찾고 요청한 기업 소통이 맞는지 다시 검증한다.
4. 같은 최종값을 반복 요청해도 안전한 멱등 동작으로 만든다.
5. 화면은 먼저 별과 상단 목록을 바꾸되 실패하면 원래 상태로 되돌리고 행 안에 재시도를 제공한다.
6. 성공한 실제 변경만 `repository_dispatch` 재빌드를 한 번 요청한다.
7. 고객 모드에서 편집 요소가 렌더링되지 않는지 자동·수동 검수한다.

### 착수 전 P0 확인사항

`.github/workflows/rebuild.yml`의 빌드 단계에는 현재 `BUILD_TOKEN` 전달이 빠져 있다.
`src/build_client.py`는 이 값이 없으면 D1 공지 게시본을 읽을 수 없어 빌드를 중단한다.
따라서 공지 게시와 주요 소통 변경 후 자동 반영을 신뢰하기 전에 다음을 먼저 처리한다.

- GitHub 저장소 Actions secret에 `BUILD_TOKEN`이 실제로 존재하는지 확인한다.
- `rebuild.yml`의 빌드 단계 `env`에 `BUILD_TOKEN: ${{ secrets.BUILD_TOKEN }}`을 추가한다.
- `workflow_dispatch`로 `whiffkorea`를 한 번 실행해 재빌드와 push가 성공하는지 확인한다.

비밀값 자체는 문서, 로그, 커밋에 절대 적지 않는다.

## 7. 새 컴퓨터 설정

### 저장소와 실행 환경

```powershell
git clone https://github.com/bluep2000-hub/growthhigh-clientpage
cd growthhigh-clientpage
python -m pip install -r src/requirements.txt
cd worker
npm install
```

개발을 시작할 때 항상 먼저 실행한다.

```powershell
git pull --rebase
```

### GitHub에 없는 인증 정보

루트 `.env`는 새 컴퓨터에 별도로 만들어야 한다. `.env.example`을 복사하고 실제 값을
보안 채널로 옮긴다. `.env`, `worker/.dev.vars`, 서비스 계정 키는 커밋하지 않는다.

- 필수: `NOTION_TOKEN`, `BUILD_TOKEN`
- 사용하는 기능에 따라: `CALENDAR_ICS_URL`, `IMAP_HOST`, `IMAP_USER`, `IMAP_PASS`
- Worker 운영 배포: 새 컴퓨터에서 `npx wrangler login`으로 같은 Cloudflare 계정에 로그인
- GitHub push: `bluep2000-hub/growthhigh-clientpage`에 쓰기 권한이 있는 계정으로 로그인

### 검증 명령

```powershell
cd worker
npm test
cd ..
python src/check_copies.py --slug whiffkorea
git diff --check
python -m http.server 8000 --bind 127.0.0.1
```

로컬 주소는 `http://127.0.0.1:8000/whiffkorea/?edit#notice`다. `file://`로 열지 않는다.

### 배포 규칙

- 루트 `index.html`을 고치면 `whiffkorea/index.html` 등 기업 사본을 반드시 다시 만든다.
- 평소 기업 재빌드·배포는 `python src/publish.py --client 슬러그 --skip-imap`을 사용한다.
- Worker API나 D1을 바꿀 때는 테스트 → 원격 마이그레이션 상태 확인 → Worker 배포 → 화면 배포 순서다.
- 작업 전 `git pull`; 다른 컴퓨터에서 같은 기업을 동시에 빌드하지 않는다.
- 자동 갱신 예약은 한 컴퓨터에서만 실행한다.

## 8. 변경하면 안 되는 안전 경계

- 고객 데이터와 비밀번호를 평문으로 GitHub에 올리지 않는다.
- `.env`, 토큰, Cloudflare secret, Notion token을 출력하거나 커밋하지 않는다.
- `c/{슬러그}.enc`가 암호화되지 않은 상태라면 배포하지 않는다.
- 사용자 요청 없이 기존의 관련 없는 로컬 변경을 되돌리거나 함께 커밋하지 않는다.
- 운영 D1을 수동 삭제·초기화하지 않는다.
- 고객 모드에 담당자 버튼, 오류 상세, 자동화 내부 상태를 노출하지 않는다.

## 10. 인수인계 완료 기준

새 작업이 다음 다섯 가지를 정확히 말하면 인수인계가 된 것이다.

1. 공지 원본은 Notion이 아니라 D1이다.
2. 자동저장은 초안만 바꾸고, 게시해야 고객 화면과 재빌드가 바뀐다.
3. 공지 편집기 운영 배포와 사용자 승인은 완료됐다.
4. 다음 기능은 담당자 전용 주요 소통 별표와 고객 화면 상단 고정이다.
5. 자동 재빌드 전에 GitHub Actions의 `BUILD_TOKEN` 전달 누락을 해결해야 한다.
