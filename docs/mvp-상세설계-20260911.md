# 클라이언트페이지 MVP 상세설계

- 기준일: 2026-09-11 · 갱신일: 2026-09-12
- 상태: 1단계 공지 편집기·2단계 주요 소통 운영 완료 · 3단계 PM 녹음 접수 이후 자동화 설계 확정·구현 전
- 1차 검증 대상: 위프코리아
- 제품 목표: 컨설팅 과정의 누락을 막고, 고객에게 현재 상태를 투명하게 보여 준다.

## 1. 이 문서의 결론

이번 MVP는 기존 시스템을 새로 만드는 작업이 아니다. 현재의 정적 클라이언트페이지, Notion 데이터, Cloudflare Worker·D1, GitHub Pages 배포 구조를 유지하면서 다음 세 부분을 개선한다.

1. **공지 편집기:** Notion에 익숙한 담당자가 미팅 중 흐름을 끊지 않고 작성할 수 있게 한다.
2. **주요 소통:** 담당자가 소통 목록에서 한 번 눌러 고객에게 먼저 보여 줄 항목을 고정한다.
3. **통화 자동화:** PM이 고객사별 접수함에 올린 삼성 통화녹음의 전사·요약·Notion·클라이언트페이지 반영을 자동 처리한다.

고객 화면은 계속 읽기 전용이다. 편집 기능, 자동화 처리 현황, 내부 오류는 담당자에게만 보인다.

## 2. 사용자와 권한

### 담당자

- 공지를 작성·수정·게시한다.
- 소통내역의 주요 항목을 지정·해제한다.
- 녹음 처리 중 `확인 필요` 또는 `실패`인 항목만 처리한다.
- 비개발자이므로 일상 운영에 코드 수정이나 터미널 명령이 없어야 한다.

### 고객사 대표·실무자

- 성과, 진행 단계, 일정, 공지, 주요 소통, 자료를 읽는다.
- 편집, 댓글, 상태 변경, 자동화 오류 확인은 하지 않는다.

### MVP 권한 경계

- 기존 `?edit` 주소와 담당자 편집 비밀번호를 유지한다.
- 잠금이 풀리면 페이지 전체에 `담당자 모드`가 적용된다. 공지 화면에만 국한하지 않는다.
- 클라이언트용 비밀번호와 담당자용 비밀번호는 계속 분리한다.
- 담당자 개인별 계정과 변경자 감사기록은 후속 단계다.

## 3. 핵심 KPI

| 지표 | MVP 목표 | 측정 기준 |
|---|---:|---|
| 접수 녹음 처리율 | 100% | 고객사별 접수함에 들어온 녹음 수 대비 Notion 기록 완료 수 |
| 자동 처리 시간 | 30분 이내 | Drive 접수부터 클라이언트페이지 배포 완료까지 |
| 접수 후 수작업 | 정상 건 0회 | 접수 이후 담당자의 파일 이동·명칭 변경·명령 실행 여부 |
| 중복 등록 | 0건 | 하나의 녹음 원본에 생성된 Notion 소통 페이지 수 |
| 실패 가시성 | 100% | 실패·확인 필요 건 중 담당자 처리함에 표시된 비율 |
| 빠른 공지 게시 | 3분 이내 | 빈 공지 시작부터 첫 게시 완료까지 |
| 주요 소통 지정 | 1회 클릭 | 목록에서 지정 또는 해제까지 필요한 클릭 수 |

`100% 처리`의 분모는 **PM이 고객사별 접수함에 명시적으로 올린 녹음**이다. 어떤 통화를
접수할지는 PM의 업무 판단이며, 접수 전 기록률은 자동화 KPI로 약속하지 않는다. 접수된
녹음·자동화 작업·Notion 기록을 대조해 이후 단계의 누락을 판별한다.

## 4. MVP 범위

### 포함

- 담당자 모드의 전역 표시와 세션 유지
- 공지 초안 자동저장과 명시적 게시 분리
- Notion과 유사한 블록 작성·선택·이동·서식 경험
- 주요 소통 지정·해제와 고객 화면 상단 고정
- PM이 선별한 삼성 통화녹음을 고객사별 Google Drive 접수함으로 업로드
- 신규 녹음 감지부터 전사·요약·Notion 기록·페이지 배포까지 자동 실행
- 담당자 전용 자동화 처리함
- 중복 실행, 인증 만료, API 제한, 부분 실패, 재시도 대응
- 위프코리아 1곳에서 검증 후 다른 클라이언트로 확장

### 제외

- 고객 댓글·확인 버튼·업무 상태 변경
- 담당자 메모, 기한, 후속조치 관리
- 모바일 네이티브 앱
- 고객별 알림 발송
- 개인별 계정·역할·감사 로그
- 공지 이미지·파일 첨부
- 휴대전화 연락처 그룹 기반 자동 선별과 자동 업로드
- Tasker·FolderSync 또는 전용 Android 수집기
- 자료 데이터룸
- 기존 고객 화면 전체의 시각적 리브랜딩

## 5. 정보 구조

### 고객 화면

현재 좌측 메뉴와 화면 구조를 유지한다.

- 기업 정보
- 조달현황
- 공지사항
- 정부지원사업·정책자금
- 기업인증·지식재산권
- 경영자문 프로젝트
- 소통 내역
- 추천 지원사업
- 자료

소통 내역 안에서는 `주요 소통`이 일반 목록보다 먼저 보인다. 고객은 누가 지정했는지나 내부 처리 상태를 보지 않는다.

### 담당자 모드

상단에 작은 고정 표시를 둔다.

`담당자 모드 · 초안/처리 필요 건수 · 종료`

- 공지사항: 편집·초안·게시 기능 활성화
- 소통 내역: 주요 지정 별표 활성화
- 처리 현황: 담당자 전용 화면 추가

고객에게는 `담당자 모드`와 `처리 현황` 메뉴 자체를 렌더링하지 않는다.

## 6. 공지 편집기

### 6-1. 핵심 목표

미팅 중 담당자가 내용에 집중해야 한다. 편집 도구를 찾고, 섹션을 만들고, 저장 여부를 판단하는 데 주의가 분산되면 실패다.

Notion과 똑같아야 하는 것은 색이나 모양이 아니라 다음 조작 모델이다.

- 빈 곳을 누르면 바로 쓴다.
- `Enter`로 다음 줄, `Backspace`로 앞줄과 합치기, `Tab`으로 들여쓰기한다.
- `/`를 입력하면 블록 종류를 고른다.
- 줄 왼쪽의 `＋`로 새 줄을 넣고 손잡이로 이동한다.
- 글자를 선택하면 서식 도구가 선택한 글 가까이에 뜬다.
- 붙여넣은 여러 줄은 각각의 블록으로 나뉜다.
- 저장 상태는 시스템이 알려 주며 사용자가 추측하지 않는다.

### 6-2. 화면 구성

1. 상단 고정 바
   - 뒤로가기 또는 `공지사항`
   - `초안 저장 중`, `초안 저장됨`, `저장 실패`, `게시되지 않은 변경사항` 중 하나
   - `미리보기`
   - 주 행동 `게시`

2. 문서 머리
   - 공지 제목
   - 공지 날짜
   - 마지막 게시 시각

3. 문서 캔버스
   - 제목과 본문이 끊기지 않는 한 줄기 문서
   - 섹션은 카드 조작부가 아니라 문서 안의 큰 구분으로 표현
   - 줄을 가리킬 때만 `＋`와 드래그 손잡이 노출

4. 보조 UI
   - `/` 명령 메뉴
   - 글자 선택 서식 툴바
   - 블록 손잡이 메뉴: 복제, 이동, 유형 변경, 삭제
   - 이전 버전 패널

현재 화면의 상시 노출된 섹션 이동 화살표, 삭제 기호, 하단 저장 바, 먼저 읽어야 하는 단축키 안내는 제거하거나 보조 메뉴로 이동한다.

### 6-3. 지원 블록

- 본문
- 제목 1·2·3
- 글머리 목록
- 번호 목록
- 할 일
- 인용
- 토글
- 코드
- 표

이미 D1 문서 모형과 Worker 검증 코드가 이 종류를 지원한다. 이미지와 첨부는 별도 보안 저장소 결정이 필요하므로 MVP에서 제외한다.

### 6-4. 초안과 게시

현재 `저장`은 D1 저장과 고객 페이지 재빌드를 한 번에 수행한다. Notion과 같은 자동저장을 만들려면 두 동작을 분리해야 한다.

#### 초안 자동저장

- 입력이 멈춘 뒤 약 1초 후 저장한다.
- 줄 이동·삭제·유형 변경은 즉시 저장한다.
- D1에 저장하지만 GitHub 재빌드는 요청하지 않는다.
- 브라우저에도 최근 임시본을 남겨 네트워크 단절 시 복구한다.
- 상태 문구는 도구막대 한곳에서만 표시한다.

#### 게시

- `게시`를 눌렀을 때만 고객에게 보이는 공지로 승격한다.
- 게시 성공 후 기존 `repository_dispatch`로 재빌드를 요청한다.
- `배포 요청됨 → 배포 중 → 고객 화면 반영 완료`를 구분한다.
- 빈 문서는 게시할 수 없다.
- 이미 저장 중이거나 충돌이 있으면 게시 버튼을 잠근다.

### 6-5. 편집기 상태

| 상태 | 담당자가 보는 것 | 가능한 행동 |
|---|---|---|
| 처음 열기 | 문서 뼈대 스켈레톤 | 기다리기, 나가기 |
| 빈 공지 | 제목과 첫 빈 줄, 작성 안내 | 바로 입력 |
| 작성 중 | 커서 주변 편집 도구 | 입력·서식·이동 |
| 초안 저장 중 | `저장 중…` | 계속 입력 가능 |
| 초안 저장됨 | `초안 저장됨` | 계속 작성·게시 |
| 미게시 변경 | `게시되지 않은 변경사항` | 미리보기·게시 |
| 오프라인 | `인터넷 연결 후 저장됩니다` | 기기 임시저장, 게시 불가 |
| 저장 실패 | 원인과 `다시 시도` | 계속 입력 가능 |
| 충돌 | 내 초안과 서버 초안 비교 | 내 내용 유지·최신본 열기 |
| 게시 중 | 진행 표시 | 중복 게시 방지 |
| 배포 대기 | `게시됨 · 고객 화면 반영 중` | 계속 편집 가능 |
| 반영 완료 | 완료 시각과 고객 화면 보기 | 새 편집 시작 |

### 6-6. 데이터 변경

기존 `notices` 표는 고객에게 공개된 게시본으로 유지한다. 이전 구조를 깨지 않기 위해 새 초안 표를 추가한다.

```text
notice_drafts
- notice_id                 notices.id와 1:1
- title
- doc                       sections JSON
- version                   초안 충돌 판정용
- base_published_version    어느 게시본에서 시작한 초안인지
- updated_at
```

- `notices.version`은 게시본 버전으로 유지한다.
- 기존 `revisions`는 게시 직전 버전을 보관한다.
- 초안 자동저장이 기존 게시본 또는 이전 버전 20개를 밀어내지 않는다.
- 게시 트랜잭션은 `현재 게시본을 revisions에 보관 → 초안을 notices에 복사 → 게시 버전 증가`를 한 묶음으로 수행한다.

### 6-7. 공지 API

| 메서드·경로 | 역할 | 재빌드 |
|---|---|---|
| `GET /notice/doc/draft?slug=` | 최신 게시본과 편집 중 초안 읽기 | 없음 |
| `PUT /notice/doc/draft` | 초안 자동저장, 초안 버전 비교 | 없음 |
| `POST /notice/doc/publish` | 초안을 게시본으로 승격 | 1회 |
| `GET /notice/doc/revisions` | 게시본의 이전 버전 목록 | 없음 |
| `POST /notice/doc/revision-to-draft` | 이전 버전을 초안으로 불러오기 | 없음 |
| `GET /notice/export` | 빌더가 게시본만 읽기 | 없음 |

기존 `GET·PUT /notice/doc`은 전환 기간 동안 유지한다. 새 편집기가 안정화된 뒤 쓰기 경로만 폐기한다.

### 6-8. 내용 범위

- 제목: 200자 이내
- 섹션 제목: 200자 이내
- 문서 전체: 직렬화 기준 512KB 이내
- 블록: 최대 1,000개
- 편집기 권장 중첩: 8단, 서버 안전 상한은 기존 50단 유지
- 표: 기존과 같이 최대 8열

상한에 가까워지면 저장 시점이 아니라 입력 중 미리 안내한다.

## 7. 주요 소통 지정

### 7-1. 화면 동작

- 담당자 모드에서 소통 목록 각 행에 빈 별 `☆`를 표시한다.
- 누르면 즉시 `★`로 바뀌고 상단 `주요 소통`에 같은 항목이 나타난다.
- 다시 누르면 해제한다.
- 저장 버튼이나 상태 선택은 없다.
- 실패하면 원래 상태로 되돌리고 그 행에서 이유와 `다시 시도`를 보여 준다.
- 고객 화면은 현재처럼 주요 소통을 상단에 보여 주고 목록에도 별을 유지한다.

### 7-2. 식별 방법

현재 빌더는 Notion 페이지 ID를 내부 용도로만 사용하고 고객 봉투에는 싣지 않는다. MVP에서는 페이지 ID를 그대로 노출하지 않고 다음 방식으로 편집용 키를 만든다.

```text
talk_key = SHA-256(Notion page id)의 앞 24자리
```

- 빌더가 암호화 봉투의 각 소통 건에 `talk_key`를 추가한다.
- Worker는 해당 고객사의 소통 목록을 Notion에서 읽고 같은 키를 계산해 원본 페이지를 찾는다.
- 키만 알아서는 편집할 수 없고 담당자 인증이 필요하다.
- Worker는 찾은 페이지가 요청한 고객사 릴레이션에 속하는지 다시 확인한다.

### 7-3. API

```text
PUT /talk/major
Authorization: 담당자 토큰

{ slug, talkKey, major: true|false }

→ { talkKey, major, rebuild: sent|failed|skipped }
```

- Notion `주요` 체크박스를 원본으로 유지한다.
- 같은 값을 다시 보내도 같은 결과를 주는 멱등 동작이어야 한다.
- 성공한 변경만 재빌드를 한 번 요청한다.
- 401은 담당자 모드 재인증, 404는 고객사 불일치, 429·5xx는 재시도 대상으로 처리한다.

## 8. PM 선별과 통화녹음 접수

### 8-1. 자동화 시작점

통화는 개인·업무 혼용 삼성폰에서 자동녹음되지만, 자동화는 휴대전화에서 시작하지
않는다. PM이 고객 통화임을 확인하고 고객사별 Drive 접수함에 직접 업로드한 순간을
자동화의 시작점으로 삼는다.

확인된 시험 기기는 `SM-S921N`(Galaxy S24 국내형), Android 15, One UI 7.0이다.
자동녹음은 켜져 있고 녹음은 `/내장 저장공간/Recordings/Call/{연락처명}` 아래
`m4a`로 저장된다. 이 기기 정보는 원본을 찾는 PM 안내에만 쓰며, 자동 수집 코드의
입력 경로로 사용하지 않는다.

```text
삼성 전화 앱의 통화녹음
  → PM이 기록할 고객 통화를 직접 선택
  → 공유 > Google Drive
  → 클라이언트 통화 미팅기록/수집대기/{고객사}
  → 여기서부터 자동 처리
```

접수 원칙은 다음과 같다.

- PM은 녹음 한 건과 고객사를 확인하고 해당 고객사 접수함을 고른다.
- 휴대전화 원본은 이동하거나 삭제하지 않고 Drive에 사본을 업로드한다.
- 삼성 전화 앱이 만든 파일명은 바꾸지 않는다.
- 고객사는 접수함 경로로 확정한다. 파일명, 연락처명이나 통화 내용으로 추측하지 않는다.
- 잘못된 고객사 폴더에 올린 파일은 처리 전에 PM이 바로잡을 수 있게 짧은 유예시간을 둔다.
- 접수 이후 정상 건에는 파일 이동, 이름 변경이나 명령 실행을 요구하지 않는다.

### 8-2. 개인 통화 보호 게이트

- **확정 조건:** 개인·업무 혼용폰이다.
- 전체 녹음폴더 동기화와 서버 측 개인·업무 분류는 금지한다.
- PM이 명시적으로 고른 녹음만 회사 Drive와 AI API로 보낸다.
- 접수하지 않은 통화의 음성파일·전화번호·연락처명·통화시각·통화 방향은 휴대전화 밖으로 보내지 않는다.
- 접수함의 고객사와 실제 통화 대상이 다르면 자동으로 다른 기업을 추측하지 않고 `확인 필요`로 멈춘다.
- 연락처 그룹, 이름 접두어와 폴더명의 철자는 고객 여부를 자동 판정하는 근거로 쓰지 않는다.

이 경계는 `docs/adr/0005-PM-선별-후-통화-자동화.md`에 기록한다. 휴대전화 자동
선별은 별도 필요가 확인될 때 다시 설계하며, 이번 MVP의 성공 조건에 포함하지 않는다.

## 9. 녹음 처리 파이프라인

### 9-1. MVP 실행 구조

```text
PM이 고객 통화녹음과 고객사를 확인
  → Google Drive `수집대기/{고객사}`에 접수
  → 회사 PC의 Drive Desktop
  → 5분 주기 Python 처리기
  → Gemini 전사
  → 구조화 회의록 생성
  → Notion 소통 내역 기록
  → 클라이언트 빌드·배포
  → D1 처리 상태 갱신
```

현재 하루 세 번 실행되는 Claude 예약 세션은 30분 KPI와 무인 안정성을 보장하지 못한다. MVP에서는 결정적인 작업을 하나의 Python 오케스트레이터로 묶고 Windows 작업 스케줄러가 5분마다 실행한다. 동시에 두 번 실행되지 않도록 잠금 파일 또는 D1 작업 임대를 사용한다.

요약 품질 규칙은 기존 `talk-summary` 스킬을 프롬프트 템플릿과 검증 코드로 옮긴다. 대화형 앱이 열려 있어야만 실행되는 구조를 일상 운영 경로에서 제거한다.

### 9-2. 처리 상태

내부 상태는 세밀하게 기록하되 화면에서는 여섯 가지로 묶어 보여 준다.

```text
received
→ transcribing
→ transcribed
→ summarizing
→ notion_writing
→ building
→ complete

어느 단계에서든 → needs_review 또는 failed
```

| 화면 상태 | 내부 상태 | 담당자 행동 |
|---|---|---|
| 접수됨 | received | 없음 |
| 전사 중 | transcribing | 없음 |
| 요약 중 | transcribed·summarizing·notion_writing | 없음 |
| 반영 중 | building | 없음 |
| 완료 | complete | 결과 열기 |
| 확인 필요 | needs_review | 접수함·파일 확인 후 재실행 |
| 실패 | failed | 원인 확인·다시 시도 |

### 9-3. 작업 데이터

```text
recording_jobs
- id                    음성파일 SHA-256
- source_relative_path  고객사 접수함부터의 상대경로
- source_name
- source_size
- source_modified_at
- received_at
- company_slug          접수함 경로로 확정, 필수
- channel               통화 또는 미팅
- occurred_at
- state
- step_version          처리 규칙 버전
- attempts
- last_error_code
- last_error_detail     비밀값과 녹취 본문은 제외
- notion_page_id        완료 후 내부 연결용
- build_run_id
- lease_until           중복 실행 방지
- created_at
- updated_at
- completed_at
```

원문 녹취와 음성은 상태 DB에 넣지 않는다. 음성은 기존 Drive에, 회의록은 Notion에 둔다.

### 9-4. 자동화 API

별도의 `AUTOMATION_TOKEN`을 둔다. 담당자 비밀번호나 `BUILD_TOKEN`을 재사용하지 않는다.

| 메서드·경로 | 사용 주체 | 역할 |
|---|---|---|
| `POST /ops/jobs/upsert` | Python 처리기 | 작업 생성 또는 상태 갱신 |
| `POST /ops/jobs/claim` | Python 처리기 | 한 작업을 일정 시간 점유 |
| `GET /ops/jobs?slug=&state=` | 담당자 화면 | 최근 처리 상태 조회 |
| `POST /ops/jobs/retry` | 담당자 화면 | 실패한 단계부터 재시도 요청 |

클라이언트 암호화 봉투에는 자동화 작업을 넣지 않는다.

### 9-5. 중복과 재실행

- 음성파일 전체 SHA-256을 작업 ID로 사용한다.
- 같은 파일명이어도 내용이 다르면 별개 작업이다.
- 동일 파일이 다시 업로드돼도 같은 작업으로 합친다.
- Notion 중복 키는 현재처럼 원본 파일 식별자를 사용하되, SHA-256도 함께 기록한다.
- 완료된 작업은 기본적으로 다시 실행하지 않는다.
- 처리 규칙이 바뀌어 재처리가 필요하면 `step_version`을 올리고 담당자가 명시적으로 실행한다.

### 9-6. 실패와 재시도

| 실패 | 자동 대응 | 최종 상태 |
|---|---|---|
| 네트워크 단절 | 다음 5분 회차에서 재개 | 대기 후 재시도 |
| Gemini 429 | `Retry-After` 준수 | 반복 시 실패 |
| Gemini 5xx | 10초·30초·60초 재시도 | 실패 |
| Gemini 인증·결제 오류 | 재시도하지 않음 | 실패 |
| 전사 결과 없음·잘림 | 원본 유지, 담당자 표시 | 확인 필요 |
| 접수함 고객사 매핑 없음 | 추측하지 않고 처리 중단 | 확인 필요 |
| Notion 429·5xx | 지수 백오프 3회 | 실패 |
| Notion 404·속성 변경 | 재시도하지 않음 | 실패 |
| 중복 Notion 기록 발견 | 새 페이지 생성 금지 | 완료 또는 확인 필요 |
| 빌드 실패 | Notion 기록은 유지하고 배포만 재시도 | 실패 |
| GitHub rate limit | 시간 기록 후 지연 재시도 | 대기 |

오류 문구는 담당자가 행동할 수 있게 번역한다. API 상태코드나 스택 추적을 그대로 보여 주지 않는다.

### 9-7. 개인정보와 AI 처리

- 실제 고객 통화에는 결제가 연결된 Gemini API 프로젝트만 사용한다.
- API 로그 공유와 모델 개선용 데이터 제공은 켜지 않는다.
- Gemini File API에 올린 임시 파일은 처리가 끝나면 현재 코드처럼 삭제한다.
- 상태 DB와 화면에는 녹취 전문을 복제하지 않는다.
- 비밀값은 저장소나 GitHub Pages 배포물에 넣지 않는다.
- 녹음·전사에 관한 고객 고지와 내부 보존기간은 출시 전에 별도 운영정책으로 확정한다.

정상 건을 감시하는 화면이 아니라, 누락될 가능성이 있는 건을 바로 발견하는 화면이다.

1. 상단 요약
   - 오늘 접수
   - 완료
   - 처리 중
   - 확인 필요
   - 실패

2. 우선 처리 목록
   - 실패와 확인 필요만 먼저 표시

4. 필터
   - 전체 고객사
   - 상태
   - 날짜

정상 처리 중인 건은 작은 진행 표시만 두고 화면을 점유하지 않는다.

## 11. 배치와 인터페이스

### PM 접수

- PM이 삼성 전화 앱에서 기록할 녹음을 직접 선택한다.
- Google Drive의 해당 고객사 접수함에 사본을 업로드한다.
- 휴대전화 원본은 자동삭제하지 않는다.
- 접수 전 단계에는 예약 작업이나 백그라운드 동기화를 두지 않는다.

### 처리 배치

- Windows 작업 스케줄러 5분 간격
- 한 번에 하나만 실행
- 실패한 작업은 해당 단계부터 재개
- 매일 1회 Drive 파일·작업 DB·Notion 기록 대조

### 배포 배치

- 게시와 주요 소통 변경은 기존 GitHub `repository_dispatch` 사용
- 같은 슬러그의 연속 요청은 현재 GitHub Actions concurrency로 마지막 실행에 합친다.
- 자동화 파이프라인이 Notion에 회의록을 쓴 뒤에도 같은 재빌드 경로를 사용한다.

### P0 진행 상태

2026-09-12에 `수집대기/위프코리아`의 Drive·Drive Desktop 경로를 확인했다.
`src/transcribe_drive.py`는 파일명이 아닌 접수함 폴더로 고객사를 결정하고, 기존 루트
녹음은 제외하며, 경로 검증과 파일 해시 중복 방지 테스트를 갖췄다 (`71b7f0f`).
같은 날 `growthhigh-client`의 유료 결제를 확인한 뒤 시험 녹음 1건을 전사했고,
사용자가 전사본과 회의록 초안을 확인했다. `src/client_mapping.py`는
`위프코리아`→`whiffkorea`를 고정하며 미등록 고객사를 추측하지 않고 중단한다.

남은 P0는 다음과 같다.

- 전사 이후 요약·Notion·배포를 상태 전이와 단계 재개가 가능한 한 회차로 연결한다.
- Python 자동화에 상태 전이와 단계 재개 테스트를 추가한다.
- 녹음·전사 운영 보존정책을 확정한다.

## 12. 안정성 요구사항

### 인증 만료

- 담당자 세션이 만료되면 작성 중 초안을 브라우저에 보존한 뒤 재인증한다.
- 자동화 토큰 오류는 반복 재시도하지 않고 담당자 처리함에 표시한다.

### API 변경

- Notion 속성명과 타입을 시작 단계에서 검사한다.
- 필수 속성이 바뀌면 빈 값으로 배포하지 않고 해당 고객 빌드를 중단한다.
- 외부 API 응답은 스키마 검증 후 사용한다.

### 데이터 오류

- 공지 문서는 기존 Worker의 HTML 허용목록과 문서 구조 검증을 유지한다.
- 녹취·요약이 비어 있거나 비정상적으로 짧으면 Notion에 자동 게시하지 않는다.
- 접수함 경로가 등록 고객사와 일치하지 않으면 `확인 필요`로 보내고 내용을 보고 추측하지 않는다.

### 중복 실행

- 공지 초안과 게시 모두 버전 번호로 동시 편집을 막는다.
- 주요 소통 변경은 원하는 최종값을 보내는 멱등 API로 만든다.
- 녹음 작업은 파일 해시와 작업 임대로 중복 처리를 막는다.

### Rate limit

- 429 응답의 대기 시간을 따른다.
- 고객별 빌드 요청을 짧은 시간창에서 합친다.
- 반복 실패는 무한 재시도하지 않는다.

### 실행 실패

- 단계별 결과를 남겨 처음부터 재실행하지 않는다.
- Notion 기록 성공 후 배포가 실패하면 Notion 페이지를 다시 만들지 않고 배포만 재시도한다.
- 실패는 담당자 처리함에서 사라지지 않으며 완료 또는 명시적 보류 전까지 남는다.

## 13. 테스트와 검수

### 자동 테스트

- 현재 Worker 263개 테스트(16개 파일)를 회귀 기준으로 유지한다.
- 초안 저장, 게시, 충돌, 이전 버전 복원 테스트
- 주요 지정 권한, 고객사 소유 검증, 멱등성 테스트
- 접수함 고객사 매핑, 파일 해시 중복, 단계 재개, API 재시도 테스트
- 빌드가 게시본만 읽고 초안을 내보내지 않는 테스트
- `BUILD_TOKEN`이 GitHub Actions에서 전달되는지 확인하는 배포 구성 테스트

### 사용성 검수

담당자가 실제 미팅 메모를 사용해 다음 과제를 수행한다.

1. 빈 공지에서 제목과 불릿 5개 작성
2. 줄 사이에 새 문장 삽입
3. 세 줄 붙여넣기
4. 한 줄을 할 일로 변경하고 들여쓰기
5. 글자를 굵게 하고 링크 추가
6. 초안 저장 확인 후 게시
7. 소통 한 건을 주요로 지정하고 해제
8. 실패한 녹음 한 건을 다시 실행

도움말을 먼저 읽지 않고 수행할 수 있어야 한다.

### 시각 검수

- 데스크톱과 모바일 웹을 한 번에 확인한다.
- 고객 모드에 담당자 기능이 노출되지 않는지 확인한다.
- 키보드만으로 편집·메뉴·게시를 수행한다.
- 포커스 표시, 오류 문구, 빈 상태, 긴 제목, 1,000개 블록 근처 문서를 확인한다.
- 모션 감소 설정을 존중한다.

## 14. 배포 순서

## 16. PM 접수 흐름과 운영 검증

혼용폰 여부는 **개인·업무 혼용폰**으로 확정되었다. `SM-S921N`, Android 15,
One UI 7.0에서 자동녹음과 `m4a` 저장을 확인했다. 연락처 그룹 자동 선별은 보류하며,
PM은 다음 한 단계만 수행한다.

1. 삼성 전화 앱 또는 내 파일에서 기록할 고객 통화녹음을 고른다.
2. `공유 → Google Drive`에서 `클라이언트 통화 미팅기록/수집대기/{고객사}`를 선택한다.
3. 업로드 완료만 확인한다. 파일 이름 변경, 원본 이동·삭제와 별도 앱 실행은 하지 않는다.

배포 합격 기준은 다음과 같다.

- 서로 다른 고객 녹음이 선택한 고객사 접수함에 정확히 들어간다.
- 접수하지 않은 개인 통화는 음성·메타데이터 모두 Drive에 생기지 않는다.
- 같은 파일을 두 번 접수해도 Notion 소통 내역은 한 건만 생긴다.
- 같은 이름의 서로 다른 녹음은 파일 해시로 구분해 각각 처리한다.
- 접수함에 들어온 정상 녹음은 30분 안에 Notion과 클라이언트 페이지에 반영된다.
- 실패한 녹음은 사라지지 않고 담당자 처리함에 해야 할 행동과 함께 보인다.
- 3일 동안 PM이 터미널 명령이나 파일 이름 변경 없이 같은 흐름을 반복한다.

휴대전화 자동 선별·자동 업로드가 실제 운영 병목으로 확인되기 전에는 Tasker,
FolderSync 또는 전용 Android 앱을 만들지 않는다.
