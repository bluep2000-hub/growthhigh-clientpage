# 클라이언트 페이지 실사용 운영

기준일: 2026-09-18. 최초 코드 인수 기준은 `ae20a98`이다.
사용자가 데이터룸 B안을 우선 선택했으며 추후 의견에 따라 변경할 수 있다.

## 담당자가 사용할 화면

- 고객: `https://client.growthhigh.co.kr/{슬러그}/`
- 담당자: `https://client.growthhigh.co.kr/{슬러그}/?edit`
- 위프코리아 데이터룸: `https://client.growthhigh.co.kr/whiffkorea/?edit#room`
- A안 비교: 담당자 주소에 `&review-room=A`를 붙인다.

고객 비밀번호로 페이지를 연다. 공지사항 또는 위프코리아 데이터룸에서
「담당자 편집」을 켜고 별도의 담당자 비밀번호로 인증한다.
고객은 자료와 즐겨찾기만 읽으며 공지·고정·주요 소통을 수정할 수 없다.

## 자료를 등록하고 공유하기

1. 노션 공유페이지 DB에서 해당 기업의 클라이언트페이지 항목을 연다.
2. `드라이브 URL`, `사업계획서 URL` 또는 `추가 링크`를 채운다.
3. 위프코리아 담당자 주소의 데이터룸에서 인증 후 「자료 반영 요청」을 누른다.
4. 「반영 요청을 보냈습니다」는 요청 접수만 뜻한다. 배포 완료를 표시하지 않는다.
5. 배포 후 「새 고객 탭에서 확인」을 눌러 자료를 확인한다.

`추가 링크` 예시:

```text
연구노트
2026년 3분기 연구노트 | https://www.notion.so/자료주소
R&D 기획
과제 기획서 | https://www.notion.so/다른자료주소
```

화면 분류는 그룹명과 자료명에 들어 있는 낱말로 결정된다.
자료가 없는 실제 기업에는 예시 자료를 만들지 않는다. 가이드북은 별도 메뉴다.
자료 링크의 Notion·Drive 열람 권한은 담당자가 해당 서비스에서 관리한다.
클라이언트 페이지 비밀번호가 외부 자료의 열람 권한을 대신하지 않는다.

노션 자료 속성을 고치는 것만으로는 재빌드가 시작되지 않는다.
「자료 반영 요청」은 자료뿐 아니라 해당 기업 페이지 전체를 기존 빌더로 재생성한다.
요청 중에는 버튼을 누를 수 없다. 실패하면 직접 다시 요청할 수 있다.
30초 시간 초과·응답 유실은 결과 미확인으로 안내하며 자동 재전송하지 않는다.
미확인일 때는 고객 화면과 「반영 진행 확인」에서 상태를 확인한 뒤 재시도한다.
인증 실패는 다시 인증한다. 기존 탭의 복호화 데이터는 요청 성공으로 갱신하지 않는다.
새 고객 링크는 `target="_blank" rel="noopener"`로 열어 기존 탭의 캐시를 물려주지 않는다.
문제가 있으면 [기존 수동 Actions](https://github.com/bluep2000-hub/growthhigh-clientpage/actions/workflows/rebuild.yml)의
`Run workflow`에 `whiffkorea`를 입력하는 경로를 사용한다.
현재 실제 데이터 재빌드 검증 범위는 위프코리아다. 다른 기업은 아래 확대 조건을
해결한 뒤 실행한다.

## 즐겨찾기에 고정하기

고정과 자동 재빌드는 현재 위프코리아에서만 제공한다. 다른 기업은 이력 이전 확인이
끝나기 전까지 📌 버튼을 표시하지 않고 API도 저장·재빌드를 거절한다.

1. 담당자 편집 인증 후 데이터룸에서 자료의 📌를 누른다.
2. 사이드바의 즐겨찾기에 올라왔는지 확인한다.
3. 자동 재빌드와 Pages 배포가 성공하면 새 고객 탭에서 결과를 확인한다.

고정은 노션 `고정 자료`에 저장되고 Worker가 기업별 재빌드를 요청한다.
다시 누르면 해제한다. 저장 실패는 즉시 표시하고 화면의 변경을 되돌린다.
재빌드 요청 실패는 고정 저장 성공과 구분해 알린다. 이때 위 Actions에서 재빌드한다.
담당자 탭의 새로고침은 저장 성공한 고정 상태를 유지한다.
기존 고객 탭은 복호화 데이터를 보관하므로 새 탭에서 새 게시본을 확인한다.

## 다른 고객사 데이터 자동화 확대 조건

자료 반영 요청 API는 `POST /room/rebuild`, 입력은 `{slug}`다. 기존 담당자 인증을
요구하고 위프코리아 제한·Notion 등록 확인 후 `requestRebuild`를 한 번 호출한다.
이 API의 Notion 쓰기는 없다. 응답의 `rebuild`는 `sent`·`failed`·`skipped`이며
`sent`만 요청 성공이다. 기업별 기존 Actions 동시 실행 정책을 사용한다.
자동화 토큰은 브라우저에 제공하지 않는다.
현재 실전 반영 시간과 파일럿 결과는 자료 변경·복구 검증 후 아래에 기록한다.

스튜디오엘비·제로백·포레스트에비뉴의 확대 재빌드도 실행 자체는 성공했지만,
새 커뮤니케이션보드에서 읽힌 공개 이력이 0건이었다. 기존 봉투의 공개 이력은
각각 100·15·100건이었다. 이 차이를 단순 성공으로 간주하지 않는다.
이번 작업이 만든 3곳의 데이터 갱신은 기존 배포본으로 복구하고 B안 화면 사본은 유지했다.
노션의 실제 공개 승인과 기존 이력 이전을 확인하기 전에는 이 3곳을 자동 재빌드 대상으로
확대하지 않는다. 이전·공개 여부는 PM의 결정이며 빌더가 자동으로 고객 공개를 켜지 않는다.
