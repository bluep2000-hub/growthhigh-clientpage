# 신규 클라이언트페이지 제작 프로세스

기준: 2026-10-02. 새 고객은 기존 화면과 비공개 Worker를 재사용한다. 고객별 코드나 예약 작업을 복제하지 않는다. **기업명 하나를 받으면 Notion 클라이언트페이지 링크부터 만든다.** 자료가 없어도 빈 타임테이블·데이터룸을 갖춘 초기 페이지를 만든다. 이 문서가 신규 제작의 실행 순서다.

## 처음 받을 정보

사용자에게 **기업명 하나**만 먼저 받는다. 기존 Notion 기업 원본은 제가 찾고, 영문 주소는 중복을 확인해 정한다. 동명 기업이 여러 행이면 활성 고객·담당자·계약·프로젝트 근거로 원본 하나를 확인해 `--company-page-id`를 지정한다. 다른 행은 병합하지 않는다. 근거가 부족하면 원본만 요청한다. 로고·계획·자료가 없어도 뼈대 제작을 기다리지 않는다. Notion 클라이언트페이지를 만든 즉시 그 링크를 먼저 전달하고, 메일·비밀번호·비공개 빌드는 그다음에 진행한다.

| 자료·결정 | 누가 제공하나 | 언제 필요한가 | 없을 때 |
|---|---|---|---|
| 기업명/기업 DB 원본, 영문 주소 | 사용자: 기업명 전달 / 제작자: 기존 DB·주소 중복 검색 | 착수 | 기업 원본 없으면 생성 전 대기. 주소는 중복 없는 후보를 정해 보고 |
| 고객 비밀번호 | 사용자 또는 담당자가 실제 `/<slug>/?edit`에서 직접 설정 | 비공개 빌드 전 | 페이지 뼈대까지만 제작. 비밀번호는 채팅·Notion·Git·명령 인자에 기록하지 않음 |
| 고객에게 공개할 자료 링크, 로고 | 사용자: 공개 범위·파일 또는 링크 / 제작자: 기존 게시 자료 탐색·연결·열람 확인 | 초기 제작 뒤, 전달 전 | 데이터룸은 빈칸으로 유지. 로고는 나중에 아이콘으로 반영 가능 |
| 1년 컨설팅 일정 원본(보통 2nd 자료) | 제작자: 해당 기업의 최신 게시된 `YYYY-MM-DD 기업명 - 2nd 자료`에서 `진행 시나리오 → 주요 로드맵` 월별 표를 자동으로 읽음 | 비공개 빌드 때 | 직접 작성한 고객페이지 타임테이블 우선. 자료·월별 표가 없으면 빈칸 유지. 3개년 시나리오는 제외하며 예상 산출물을 완료 실적으로 표시하지 않음 |
| 첫 공지의 내용, 고객 전달 여부 | 사용자/담당자 | 고객 전달 전 | 공지는 비워 두고 주소·비밀번호를 임의로 발송하지 않음 |

## 단계별 로직

| 단계 | 제가 실행·확인하는 일 | 사용자/담당자가 하는 일 | 완료 기준 |
|---|---|---|---|
| 1. 원본 조사 (`inspect`) | 기업 DB 단일 행, 기존 고객페이지·주소 중복, 게시 자료 후보, 소통 분류, 기존 프로젝트·소통을 확인 | 기업명만 전달. 검색 결과에 기업이 없거나 여러 곳이면 정확한 원본 지정 | 고객 원본과 주소가 한 곳으로 확정 |
| 2. 페이지 링크·초기 뼈대 (`prepare`) | Notion 고객페이지를 만들고 **실제 링크를 즉시 전달**. 기업 관계, 고객별 프로젝트·공개 소통 보기, 데이터룸 자료칸, 빈 12개월 타임테이블, 운영 녹음 접수함의 고객 폴더·주소 매핑 생성. 기존 것이 있으면 재사용 | 로고가 있으면 전달. 녹음 접수함 위치가 둘 이상일 때만 실제 운영 폴더 지정 | Notion 링크 전달, 빈 영역·녹음 폴더/매핑 확인 |
| 3. 기존 이력 (`mail`) | 다우오피스 전용 메일함, 없으면 공용함의 정확한 `[기업명]` 제목만 찾는다. 제작 에이전트가 발신자·수신자·본문을 확인해 고객과 주고받은 메일의 Message-ID만 승인한다. 승인한 메일만 원본 DB·고객 공개 보드에 반영하고 다시 읽어 확인한다 | 분류가 애매한 메일의 공개 여부만 결정. 원본이 없다면 그 사실 확인 | 검색 범위 경고 없음, 승인 건만 공개되고 제외 건은 표시되지 않음 |
| 4. 인증·비공개 빌드 (`build`) | 비밀번호 등록 확인 뒤 대상 고객만 D1에 저장. 비로그인 주소·자료 링크·타 기업 데이터 격리를 확인 | `https://client.growthhigh.co.kr/<slug>/?edit`에서 비밀번호를 직접 설정. 고객 비밀번호로 로그인해 실제 화면의 자료·소통·일정·타임테이블 표시 확인 | 빌드 `saved`, 담당자의 고객 화면 확인과 권한 검수 완료 |
| 5. 내용 보강·전달 | 받은 일정 원본을 고객 표와 요약에 옮기고, 공개 승인 자료를 데이터룸에 연결한 뒤 재빌드·검수. 상태와 남은 빈칸 기록 | 일정·자료 공개 범위 확인, 첫 공지 작성·게시, 최종 고객 전달 결정 | `제작 완료`와 `고객 전달 완료`를 별도로 기록 |

운영 명령은 저장소 루트에서 순서대로 실행한다. 중단되면 원인을 해결한 뒤 같은 단계부터 재실행한다. `inspect`는 읽기 전용이고, `prepare`·`mail`은 중복 생성을 피한다.

```powershell
.venv\Scripts\python.exe src/onboard_client.py --company 고객사명 --slug 영문주소 --step inspect
.venv\Scripts\python.exe src/onboard_client.py --company 고객사명 --slug 영문주소 --step prepare
# 제작 에이전트가 다우오피스 메일을 읽고 고객과 주고받은 건만 승인한 뒤 실행
.venv\Scripts\python.exe src/onboard_client.py --company 고객사명 --slug 영문주소 --step mail --approved-message-id 검토한_ID
.venv\Scripts\python.exe src/onboard_client.py --company 고객사명 --slug 영문주소 --step inspect
# 담당자의 비밀번호 저장 확인 후
.venv\Scripts\python.exe src/onboard_client.py --company 고객사명 --slug 영문주소 --step build
```

공개할 메일이 여러 건이면 `--approved-message-id`를 건마다 반복한다. 고객별 날짜·제목·건수·민감 내용 범위와 목적지(해당 고객의 노션 소통 DB 및 보호된 고객페이지)를 제시해 본문 공개 승인을 받는다. 승인 전에는 `--step mail`을 실행하지 않는다. 실제 인증값·주민번호·인증서 전달은 제외한다.

여러 고객을 병렬로 제작하라고 요청하면 에이전트별 고객을 나눠 조사·준비·검토한다. 인증 요청은 준비된 고객끼리 묶는다. 공통 코드·고객 매핑·배포·관리 DB는 한 담당자가 통합하며, 각 고객의 인증·공개 승인·저장 검증 조건은 그대로 지킨다.

## 판단 규칙

- **초기 제작과 내용 완성은 다른 상태다.** 자료·계획·공지 0건은 초기 제작을 막지 않는다. 빈 값과 수집 실패는 구분해서 보고한다.
- **메일 수집은 빌드와 별도다.** `build` 성공만으로 과거 메일 연동 완료라고 하지 않는다. 다우오피스 메일을 Gemini에 보내지 않는다. 제목만 일치한 내부 전달·시스템 알림은 제외하고, 제작 에이전트가 본문과 수신 대상을 확인한 Message-ID만 `mail` 명령에 지정한다. ID를 지정하지 않으면 쓰기를 거부한다. 애매한 건은 공개하지 않는다. 기존 행의 담당자 공개 설정은 바꾸지 않는다. 최초 검색은 폴더당 최대 5,000통이며 상한·접속 오류가 나면 완료로 표시하지 않는다.
- **고객 공개 자료만 연결한다.** 내부 Notion 링크가 있다는 사실은 공개 승인이나 고객 열람 성공을 뜻하지 않는다. Notion `public_url`이 있는 자료를 연결하고 실제 열리는지 확인한다. 일정의 미확정 월, 예상 성과는 임의로 채우지 않는다.
- **2nd 자료의 기존 형식을 읽는다.** 월별 표의 `주요 실행 항목`·`자금조달` 헤더와 곡선 따옴표를 지원한다. 구형 `진행일정` DB는 `주요항목`·`일정`·`상세내용` 원본을 읽는다. 명시된 연월과 떨어진 구간을 유지하고, 상시 항목에 월을 만들지 않는다. 원본이 13개월이면 마지막 달까지 표시한다.
- **메일 본문을 기준으로 중복을 확인한다.** 같은 날짜·제목이라도 본문이 다르면 각각 보존한다. 같은 본문을 다른 수신자에게 보낸 사본은 소통 보드에 한 번 표시한다. 기존 URL 칸의 원본 링크 식별자를 재사용하며, 담당자가 편집한 본문·공개 설정은 덮어쓰지 않는다. 원본이 모호하면 해당 묶음만 확인 대기로 남긴다.
- **로고는 고객 Notion 페이지 아이콘에서 읽는다.** 작은 화면에서 글자가 뭉개지는 로고면 심볼 파일을 요청하거나 심볼만 사용한다. 원본이 없으면 기본 표시로 시작한다.
- **운영 배포와 데이터 갱신을 구분한다.** 고객 내용 변경은 해당 고객 비공개 빌드로 반영한다. 공통 화면 코드를 수정한 경우에만 코드 배포가 추가로 필요하다. 녹음 자동화는 폴더·매핑 생성과 실제 예약 처리 성공을 별도로 확인한다.
- **전달은 담당자 결정이다.** 첫 공지는 고객페이지 편집 화면에서 작성하고, 고객용 주소는 `https://client.growthhigh.co.kr/<slug>/`이다. 고객에게 주소·비밀번호를 보내는 일은 명시적으로 지시받은 뒤 수행한다.
- **제작 완료 후 관리 DB에 정리한다.** 기존 `클라이언트페이지 관리` DB의 담당자 그룹 아래에 기업정보·노션페이지 관계와 `클라이언트페이지` 제목 칸의 관리자 바로가기(`/<slug>/?edit`)를 등록한다. DB 구조, 권한 보기, 기존 권한 기록은 유지한다.
- **추천사업은 고객페이지에서 관리한다.** 담당자 편집 모드에서 큐레이션 사이트의 같은 공고 데이터를 검색하고 추가·제거·고정한다. 등록 고객 모두 공통 D1 목록을 쓰며, 큐레이션 저장소 `clientpage-clients.js`에 기업명/주소를 등록해 공개 검토서 목록도 같은 선택을 읽도록 한다. 기존 Firestore 추천이 있으면 최초 연결 때만 보존하고 반복 복제하지 않는다.

## 다음 고객 착수 시 대화 흐름

1. `기업명`만 받는다. 기존 기업 DB와 주소 중복은 제가 확인한다.
2. 제가 `inspect`·`prepare`로 Notion 클라이언트페이지를 만들고 **그 링크를 먼저 전달**한다.
3. 제가 기존 메일을 읽고 고객과 주고받은 건만 선별해 연결한 뒤 공개·제외 건수를 보고한다. 비밀번호 설정 링크를 전달한다.
4. 저장 완료 회신 뒤 제가 `build`하고, 담당자가 비밀번호로 로그인해 화면을 확인한다. 일정/로고/자료가 나중에 오면 같은 고객페이지에 순차 반영한다.
5. `초기 제작 완료 / 내용 보강 대기 / 고객 전달 완료`를 구분해 마지막 상태와 다음 한 행동을 보고한다.

추가 기능의 고객별 제한과 검수 항목은 `docs/다음-클라이언트-착수-체크리스트.md`, 예약 갱신·녹음 운영은 `docs/현재-예약자동화-운영.md`를 따른다. 실제 고객 데이터·비밀번호·녹음 원문은 GitHub에 저장하지 않는다.
